# 流水线性能策略与基准

本轮实现五项调整：默认合并 Synopsis、章节阶段追踪、质量驱动的选择性 Polish、共享 AttemptBudget，以及按需 Review。Scene 并发与提交前硬门沿用现有实现。

## 默认行为

- Synopsis：优先读取任务卡的 synopsis；没有时用目标与场景蓝图确定性构造。保留任务卡的 state_changes 和 foreshadow_execution，不增加独立 LLM 请求。
- Polish：对长度异常、截断、重复、语言污染、脚手架、beat 缺失、时间线、scope、禁词或跨场重叠命中的场景调用。字数位于质量策略容许范围内且检查通过的场景原样保留。恢复的场景也重新检查。Polish 保留结构化场景的 beats_covered 等元数据。
- Review：先检查确定性硬门、语言、阻断禁词和严重字数不足（低于全章目标的 60%）。失败时返回可定位的修复问题，不请求文学评分；硬门通过后单评。首评分数距离 publication_line 或 soft_publication_line 不超过 2 分时，补两票取中位数。极差大于 15 时合并各票具体问题，进入自动修复，修改正文后再评审。技术性无效票失败关闭。同一最终文本在修复循环中也可复用缓存，修改正文后自动失效。
- Budget：同一 `_run_with_retry` 内，初次生成、重试、重排、修复和线程池任务共用预算。预算在实际 HTTP 请求前扣减，因此底层退化重试同样计数。Router 负责传输故障重试，底层 Client 每个 Router 尝试只发送一次传输请求，退化的成功响应仍可跨温度重试并消耗共享限额。
- 达到预算后不再发新请求，提交入口拒绝执行，结果含 budget_exhausted 与 quality_repair_exhausted，pending_human_review=false。运行记录中保留原因，下一次显式运行可以使用新的预算。进程外重新启动不共享内存预算。

在项目数据根目录的 `config/runtime_config.json` 中可设置以下非密钥配置；不要覆盖已有其它字段：

```json
{
  "pipeline": {
    "merge_synopsis_into_directing": true,
    "skip_polish_on_target": true,
    "review_policy": "on_demand",
    "review_borderline_margin": 2,
    "attempt_budget": {
      "max_llm_calls": 48,
      "max_scene_attempts": 3,
      "max_review_rounds": 2,
      "max_review_calls": 6,
      "max_wall_seconds": 300
    }
  }
}
```

这些值也是缺省值。scene_attempts 包含首稿及后续 generate_scene、focused、beat-split 救援调用；HTTP 层内部重试另由全章 max_llm_calls 控制。缓存命中与确定性拒绝不消耗 Review 轮次；一轮边界三评消耗一轮与三次评审调用。

`merge_synopsis_into_directing=false` 可使用独立缩写；`skip_polish_on_target=false` 可恢复对新场景逐场润色；`review_policy=legacy` 可使用旧评审策略。共享预算仍生效。

## 追踪与统计

每次运行写入 `audit/latency/chapter_<章号>_<run_id>.json`，结果字典附带 trace_path。记录包括：

- 全章 wall_s、阶段起点与 wall_s、场景编号、成功/失败状态。
- world_sim、director、synopsis、write、scene.wall、polish.wall、确定性门、修复、Review 和 commit_io。
- 线程池排队、速率限制等待、重试退避和实际 provider 请求耗时。
- 实际请求数、重试请求数、失败请求数、返回的 token usage、预算使用量。

不写入正文、prompt、密钥或异常原文。并发场景及嵌套阶段存在重叠，**不能把各阶段耗时相加当作全章耗时**。失败请求通常没有供应商 usage，其 token 成本未知；流式响应缺少 usage 时沿用 Client 的估算。

## 真实验证中发现的重试问题

Agnes 3.0 Flash 首次首章试跑未提交：约 296 秒、13 次请求，导演阶段约 196 秒。开场密度门要求的 external_event、irreversible_state_delta、world_anomaly_signal 未写入导演 Craft 输出契约，且骨架生成忽略了上轮校验反馈，造成重复规划。已补齐这些字段、反馈注入与对应回归测试，并为导演缓存增加契约版本。未放宽质量门。该失败样本不能作为成功章节的吞吐基准。

预算终止异常现在也直接穿过 Provider 与 Failover 层，避免到达限额后仍继续退避或切换供应商。

场景补写并发度现在读取实际执行请求的 Refine router，而非 Outline router；当前 Agnes 配置分别为 Refine=4、Outline=1。此前误用 Outline 的设置会把四场补写串行化，已加入线程并发行为回归测试。

导演合并任务卡时，chapter_num 始终使用调用方传入的章号；LLM 漏写或误写章号不会再导致第 0 章正文、日志或 journal。此修正同样纳入导演缓存版本。


## 连续生成与可恢复发布

单章目标维持 10,000 字，现有评分、字数、语言、密度、连续性与发布硬门不变。默认串行推进章节，章内场景、补写和润色继续并发。一个项目的生成过程有跨进程互斥；下一章必须看到上一章完整且 hash 校验通过的正式 checkpoint。已正式发布的章节直接返回，不再次调用模型。

发布事务同时保护正文、缩写、大纲、备份、checkpoint、状态机、session tree、索引、短期记忆、世界状态 JSON、SQLite 和连续性审计。写入失败时恢复事务前状态；进程异常退出时，下次启动恢复尚未完成的事务。成功必须同时具备正式 checkpoint 与 COMMITTED 状态，force-best 草稿不算正式发布。读取正式结果应使用 verify_published / is_chapter_committed；直接读取输出目录不具备事务隔离。

世界状态快照取应用变更后的状态。未获应用授权的变更仍写 deferred 审计。质量重规划会归档旧场景、清空冻结任务与缩写，再规划一次；不会把旧场景混进新任务。HTTPX 连接池在章内线程及后续章节之间复用，并在 orchestrator.close() 时关闭。

场景 prompt 按本场目标及 beat 数动态分配字数，修正 2,500 字场景却要求每拍 150–250 字的冲突。这仅纠正生成指令，不调整验收门槛。

故障注入回归覆盖：checkpoint 保存前后失败、部分正文写入失败、进程中途退出、SQLite/JSON 同步回滚、状态记录失败、三章提交后重启、重复提交跳过、前章失败阻断后章，以及重规划归档。三章提交测试使用固定正文，不代表真实模型通过质量验收。


真实 10,000 字试跑进一步定位并修正：恢复场景曾因不在“新场景”集合而跳过有界补写；现在按实际篇幅判断，合格恢复稿仍零请求。连贯但偏短的场景默认直接走既有并发补写，避免先付费整场重生、随后又补写；如需原路径可设置 pipeline.regenerate_short_scenes=true。润色请求携带确定性检查定位的问题及原稿字数，并明确保持有效情节和篇幅；最终硬门仍独立检查。

当前本地 Agnes 配置为 900 秒、48 次请求、6 次单场生成、5 轮/15 次评审、4 轮章级自动修复；这是 10,000 字验证的资源边界，与上文通用默认值不同。禁止将耗尽预算后手动续跑的多轮总耗时省略为单轮成功耗时。


正式 production_runner 默认使用阶段路由，避免注入同一客户端后绕过各阶段模型/响应模式/并发设置；pipeline.phase_routing=false 保留旧入口。恢复运行保留场景 journal；顺序模式默认不再叠加 runner 层的整章重规划，避免自动开启新预算。完整性检查使用真实完成章号集合，并排除 force-best 草稿。

真实评审中 Agnes 3.0 Flash 连续返回 reasoning-only，随后到达 900 秒上限。Polish/Refine/Review 因此显式请求 reasoning_effort=none，导演及正文仍保留原设置；评分维度、归一化、边界补评及发布分数线不变。review_llm.temperature 现在实际传给独立评审 provider，避免继承生成温度 0.85。可选软修复会在调用前检查单场剩余额度；额度不足时保留软提示，不发请求，也不因可选修复破坏后续必需评审。

本地单场额度改为 6 的原因：真实路径包含初稿、确定性验证、连续性/密度修复与语言重试，原来的 3 次在全章预算仍有余量时反复提前终止。全章 48 次实际请求、900 秒时限和质量门保持不变；这是资源调度调整，不代表已通过连续发布验收。

2026-10-25 回归：349 项相关 pytest；早前另有 5 项基础 unittest；真实运行记录见工作区 `/workspace/benchmarks/连续生成验收报告.md`。禁止用离线测试通过替代真实连续 3/10 章验收。


统一生成约束现在从当前项目 config/leak_terms 的匹配章节配置读取硬词、当夜/天亮边界与受控例外，并携带真实 timeline_anchor 和 forbidden_checks。初稿、补写、润色及路由器上的直接修复请求使用同一份信息。词表按项目路径、文件修改时间和大小缓存，修改配置后失效；未匹配的后期章节不继承婴儿篇词表。此改动补齐生成输入，未修改 scope/canon 判定或受控例外。

确定性预检未通过时的占位 score=0 不再触发“文学低分整章重写”；真实文学低分仍保留原有升级路径。诊断评审已用一次真实请求返回完整 9 维 JSON，失败稿得分 49.2；这仅证明评分响应协议可用，不代表章节通过。真实连续发布结果必须另查验收记录。


可选锚点修复的已覆盖项现在会从待修复集合移除（此前检查通过仍残留，造成无效重写）。候选写回前检查中文纯度及相对原稿的篇幅；含新增英文或缩水超过 15% 的可选候选保留原稿，避免语言门执行后再次引入污染。未修改最终语言门、评分门或字数策略。


人物 Bible 按匹配标题保留属性段落，逐场优先传入本场人物，避免仅取含名字的一行而丢失设定。正文现在实际接收全章缩写、事件触发的伏笔计划及绑定本场的必写项；系统指令不再要求每场重复执行全章伏笔。

场景修复目标超过两场时，按严重程度与剩余额度选取两场，不再全部跳过。修复请求携带该场完整原文、前场结尾及后场开头，后续修复承接本轮已修订的前场；普通场景请求失败不丢弃其它场的成功修复，预算终止仍立即传播。最终确定性门和补长完成后同步场景 journal，恢复时保留最新正文。

延迟报告保留 success 的执行语义，另列 published/unpublished 分组。草稿 success=true 不等于正式发布，成功草稿不得混入正式章节吞吐数据。


## 自动质检与修复（2026-10-25）

机器评审不稳定、分数不足、阻断性评审问题及确定性检查失败统一进入自动修复。确定性门通过后先对审稿点名段落做最多三处锚点替换，沿用既有篇幅变化护栏，验证后写入 journal 并重新质检；无法形成合规修改时再复用场景定点修订、规则修复及文学修订。这些路径未改变正文时，执行一次针对评审意见的全文修订，再复检。只有正文确实改变才重新请求文学评分；同稿不反复抽票凑分。评分分歧时保留各票指出的问题供修订使用，不以合票掩盖分歧。

`pipeline.max_chapter_fix_rounds` 默认 2，允许配置 0～10。初评与修复后复评共用原有 HTTP、单场、评审轮次、票数和时间预算；不会因进入修复自动刷新预算。稳定评分达到原发布线、无阻断评审问题、确定性门通过后，仍须通过原有提交前检查与发布事务。10,000 字目标和质量/字数门不变。

达到轮次上限、正文不再变化或共享预算耗尽，保存到 `chapters/draft/chapter_N.txt`，诊断保存到 `audit/quality_repairs/chapter_N.json`，标记 `quality_repair_exhausted=true`、`pending_human_review=false`，停止当前连续生成，不发布失败稿，也不推进后章。诊断包括每轮文本 hash、评分、票数与问题。新增质量失败记录写入项目自己的 `audit/quality_failures.jsonl`，不再追加 `needs_human_review.json`；历史待审记录保留。

新增回归覆盖自动修复至正式提交、不同失败类型、评分仍不稳定、硬门拒绝、全文修复兜底、同稿停止、预算耗尽落盘与外层禁止重复重试。离线回归不代表真实模型连续 3/10 章验收通过。
